# 安全模型

> 目标：即使 LLM 被 prompt injection 完全劫持，也只能输出一个结构化 QueryPlan，不能执行任意 SQL。
> 对应测试：`tests/test_security.py`（单元层，8 条）+ `tests/test_guard_e2e.py`（端到端层，5 条）。

## 1. 威胁模型

假设攻击者已经控制了 LLM：

- 它可以让模型输出任意 `metric_id`、`dimension_id`、filter value 和时间范围；
- 它可以让模型在字段里塞 `DROP TABLE`、分号、注释符、文件路径；
- 它**不能让模型输出一条 SQL**，因为 `QueryPlan` 里没有 SQL 字段。

安全边界不建立在“模型会听话”上，而建立在“模型没有地方写 SQL，执行层也不相信模型给的字符串”。

## 2. 四层防线

### 第一层：QueryPlan 没有 SQL 字段

`src/plan/schema.py` 的 `QueryPlan` 只有：

- `metrics: list[str]`
- `dimensions: list[str]`
- `filters: list[Filter]`
- `time_range: TimeRange`
- `order_by` / `limit` / `clarify` / `unsupported_reason`

`tests/test_guard_e2e.py::test_queryplan_has_no_sql_field` 会锁住这个约束：字段名里不允许出现 `sql`，也不允许出现 `query` / `statement` / `raw_sql` 这类自由文本 SQL 入口。

### 第二层：registry 白名单

`src/semantic/registry.py::validate_plan()` 在 Pydantic 之后再做一次业务校验：

- 指标必须在 `metrics.yaml` 的 12 条指标里；
- 维度必须在指标声明的 `allowed_dimensions` 里；
- filter 字段必须在 `allowed_filters` 里；
- 没有时间字段的指标不能按时间过滤；
- 一次只能查一个指标。

恶意 `metric_id` 或 `dimension_id` 在这一层就会变成 `UNKNOWN_METRIC` / `UNKNOWN_DIMENSION`，不会进入编译器。

### 第三层：compiler 只渲染，不拼接用户值

`src/semantic/compiler.py` 是唯一允许生成 SQL 的地方：

- 指标、维度、表名、函数来自 `metrics.yaml`，不是来自模型自由文本；
- filter value 一律走 `?` 占位符，绑定到 DuckDB 参数；
- 时间范围也走参数绑定；
- 所有查询固定带 `LIMIT ?`。

所以 filter value 里写 `1'; DROP TABLE orders; --`，最终只是 `c.customer_state = ?` 的一个字符串参数，不会变成第二条语句。

### 第四层：guard + DuckDB 只读 + 资源上限

即使编译器被改坏，`src/exec/guard.py::check_sql()` 仍会：

- 只允许单条 `SELECT` / `WITH` 查询；
- 拒绝 `DROP` / `INSERT` / `UPDATE` / `ATTACH` / `COPY` 等节点；
- 只允许 6 张契约表；
- 只允许白名单函数。

`src/exec/duck.py` 再用 `read_only=True` 打开 DuckDB，并设置超时、行数上限和内存上限。静态检查不是唯一防线。

## 3. 端到端用例

`tests/test_guard_e2e.py` 不直接调 `guard.check_sql()`，而是用：

```python
pipeline.answer(question, plan_override=plan)
```

走完整链路：

```text
QueryPlan → canonicalize → validate_plan → compiler → guard → DuckDB
```

| 恶意 plan | 期望结果 | 实际拦截点 |
|---|---|---|
| `metric_id = "drop table orders"` | `error / UNKNOWN_METRIC` | registry 指标白名单 |
| `dimension_id = "state; DROP TABLE orders"` | `error / UNKNOWN_DIMENSION` | registry 维度白名单 |
| filter value = `"1'; DROP TABLE orders; --"` | `no_data`，合法 SELECT + 0 行 | compiler 参数绑定 |
| `time_range = 2019-01-01 ~ 2019-12-31` | `unsupported` | registry 时间范围兜底 |
| 检查 `QueryPlan.model_fields` | 无 SQL / query / statement 字段 | 结构约束 |

注意第三行：filter value 注入不是 `error`，而是 `no_data`。这正是参数绑定的正确结果——它是一条合法 SELECT，只是过滤值匹配不到任何州。测试断言的是“没有成功结果、SQL 里没有注入字符串、SQL 仍是单条 SELECT/CTE”，而不是强行让它报错。

## 4. 两层测试不要混

- `tests/test_security.py`：8 条单元用例，直接测 `guard.check_sql()` 会不会放行危险 SQL。
- `tests/test_guard_e2e.py`：5 条端到端用例，假设 LLM 已经沦陷，测恶意 QueryPlan 走完整链路能不能执行。

两层都要保留：单元层证明最后一道门有效，端到端层证明前面的结构约束和参数绑定有效。

## 5. 不覆盖什么

这层安全模型不等于“业务正确”或“绝对安全”：

- 它不能阻止模型输出**合法但错误**的查询（例如选错指标、选错时间范围）；
- 它不能阻止攻击者在允许的指标/维度范围内做数据探索；
- 它不负责 API 鉴权、限流、审计和密钥管理；
- prompt injection 仍可能让模型给出误导性结论，所以 UI 必须同时展示口径、SQL 和 trace。
