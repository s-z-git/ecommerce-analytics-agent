# 数据字典（Olist）

> 数据来源：Kaggle "Brazilian E-Commerce Public Dataset by Olist"，实际覆盖 2016-09-04 ~ 2018-10-17，货币 BRL。
> 入库快照：2026-11-03，用 commerce 环境运行 scripts/build_db.py；数据截止 **2018-10-17 17:30:18**。
> 这份文档写的是"坑"，不是"字段罗列"——字段名看 `scripts/build_db.py` 里的建表语句就是全部真相。
> 指标口径与 12 条契约见 `docs/指标契约.md`；本文档不重复列指标定义。

### 坑 1：customer_id ≠ 客户

`customer_id` 是"每笔订单一个"的匿名 id，同一个真人下两单会有两个不同的 `customer_id`。
实测 99,441 行 customers 对应 99,441 个 `customer_id`，但只有 96,096 个 `customer_unique_id`；按 `customer_id` 算复购永远是 0，按 `customer_unique_id` 算全客户复购 2,997 人（3.12%）；当前 repeat_rate 口径为有有效订单客户 2,888/94,990=3.04%。
**所有"客户数 / 复购"必须用 `customer_unique_id`。**

### 坑 2：多张一对多表不能直接 join

`order_items` × `payments` × `reviews` 直接三表 join，行数会相乘，GMV 会重复。
实测：112,650 条 order_items 直接 join payments 后 117,601 行，再 join reviews 后 117,329 行；全量 item GMV 从 13,591,644 变成 14,141,001（净 +4.0%）。在同时有支付和评价的订单上，纯 fan-out 约 +5.0%；inner join 又丢掉 749 个没有评价的订单（约 12.5 万 GMV，-0.9%）。局部订单最多 29 条支付、3 条评价，重复会更严重——不是"全量翻几倍"，但结果一定不可信。
**做法：子表各自按 `order_id` 聚合，再 join 聚合结果**（见 metrics.yaml 的 `ctes`）。

### 坑 3：分母不一样

- GMV / 订单数：排除 `canceled`、`unavailable`；实测这两类合计 1,234 单（1.24%）
- 取消率：分母是**全部订单**；`canceled` 625 单（0.63%），若把 unavailable 也算"取消"则 1.24%
- 延迟率：分母是**已送达订单**；实测 7,826/96,470 = 8.11%（判定：`delivered_customer_date > estimated_delivery_date`），按全部订单算会变成 7.87%
口径混用是最容易出问题的地方。

### 坑 4：时间不能按今天算

数据购买时间实测为 **2016-09-04 21:15:19 ~ 2018-10-17 17:30:18**。
但首尾月份几乎是空的：2016-09 只有 4 单、2016-10 324 单、2016-11 没有订单、2016-12 只有 1 单；2018-09 只有 16 单（仅 1 单有效）、2018-10 只有 4 单（全部无效）。做月趋势时建议只用 **2017-01 ~ 2018-08** 的完整月份。
**锚定 `MAX(order_purchase_timestamp)`**。

### 坑 5：状态字段不只有 delivered

`order_status` 实测有 8 种：delivered 96,478、shipped 1,107、canceled 625、unavailable 609、invoiced 314、processing 301、created 5、approved 2。
统计"已送达"要显式过滤，别默认全是 delivered。

## 3. 写 gold SQL 时的注意事项

1. 时间区间用左闭右开 `>= start AND < end` 更安全
2. 比率类结果用 `* 1.0` 转浮点，否则整数除法会截断
3. 分母用 `NULLIF(..., 0)` 防除零
4. 品类为空用 `COALESCE(product_category_name, '未分类')`
5. 排序遇到并列时补第二排序键，否则你和系统返回的顺序可能不同（评测按集合比较，但人工看会困惑）
